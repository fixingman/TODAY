Requested by Can on October 28, 2026. This slice follows the shipped mail ownership repair. It does not change OAuth scopes, routing, mailbox access limits, automatic sending or other feedback domains.

## Concrete mechanism

**Mail context:** an optional “not this thread” action rejects the exact displayed thread for its current task. Persist before hiding; Undo/show email restores it without a lookup. An explicit “try other email” permits one replacement lookup per focus visit, using the existing grounded query and at most five threads / ten recent messages each. Filter the rejected thread IDs locally before the unchanged relevance/ambiguity guards. No automatic lookup on a reaction and no preference about a sender or other task. Failed/empty alternatives retain the hidden original and its restore action.

**Draft wording:** only an actually displayed draft exposes an optional “wording” row with “hard to follow” and “too formal”, revision/toggle-off, Undo and clear all. Each explicit choice targets that exact draft digest, current owner/text/mail grant/selected message and original cache expiry. No draft prose is persisted. Choices guide a later explicitly requested draft; they never rewrite the current result automatically. An explicit “try another draft” permits one replacement per visit; failure preserves the previous draft and its Mail/Copy action. Copying, opening Mail, editing elsewhere, completion, silence and hiding are neutral. Never infer a sent email or successful outcome.

Scope decision (Can, October 28): the same fixed concerns may guide future Gmail drafts for other tasks on this device. Thread rejection remains task-local. Only the two code-owned concern values may reach a draft writer; no old emails/drafts, task history, identities, counts or scores. Web/Trello/Focus/feeling feedback stays separate. The current task and selected message snippet remain the existing factual draft inputs. Missing or invalid wording concerns retain the baseline; a whole-result rejection never supplies an invented wording reason. Compatible fixed concerns can combine only within their approved scope.

## Data boundary, specified before runtime writes

Reuse only an optional `feedback` object on existing `gmail_enrichment_<taskId>` entries; no new localStorage prefix, sync/backup field or independent profile. Existing mail context has a 24-hour lifetime. Feedback cannot outlive or renew its supporting entry's original expiry, including when another selected thread replaces it. Exact retained task/text, owner policy, current mail grant and selected result govern validity; unchanged zone moves retain ownership but only undone Today tasks can request/deliver.

Record shape: `{policy:1, expiresAt, context?, wording?}`; `context` is `{at, hidden, rejectedThreads}` and `wording` is `{concern, at, draftId, sourceId, writer, scope}`. Separate timestamps prevent a later context vote from reviving cleared wording (or the reverse). Its draftId is a SHA-256 exact-draft digest (sensitive identity, not anonymization), never draft text. Rejections are at most five existing thread IDs per owner, each bounded to 128 characters. Optional feedback is capped across the existing Gmail entries at **20 supported owners / 16,384 UTF-8 bytes**, evicting oldest feedback only rather than enlarging mail retention or deleting unrelated accepted context. One current concern per owner, no event history. Invalid/expired/oversized feedback is dropped, not interpreted as a vote. UI disclosure explains the selected scope and up-to-one-day lifetime before a choice is recorded.

Forget/reconnect/changed grant, true task edits/deletion, cache expiry, explicit feedback clear and local/incoming clear-all-memory remove support and pending influence. Existing memory-clear watermark rejects replayed old feedback. AI Forget clears wording guidance; changing the active provider/key fences requests. Feedback stays excluded from Dropbox backup/merge/Restore (size budget +0, schema 5.5 unchanged); incoming task/source changes still invalidate it. Old clients ignore optional fields and may discard them on a real cache replacement. Older-client rollback requires discarding local Gmail cache prefixes because old clients do not understand hidden feedback. Never transfer derived sensitive concerns to another surface.
