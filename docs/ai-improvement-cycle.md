## What should improve through use

TODAY should become better at choosing when to help, choosing supported content, and expressing that content in a way that lands. These are three separate outcomes. A well-written unsupported claim is still wrong; an accurate sentence can still be useless; a useful action can still be expressed badly. More requests, changing sentences and model-awarded scores are not evidence of improvement.

The ordinary-use cycle is:

**Current evidence → eligible help → valid result actually shown → optional reaction or meaningful action → bounded, current guidance → the next eligible result.**

There is no daily review task for Can. No dashboard, mandatory explanation, settings panel, background experiment or repeated console packet is part of this cycle. Some surfaces need an optional feedback control added before they can adapt honestly. Others already have useful actions; they should reuse them rather than add redundant ratings.

The cycle personalizes the app's next eligible response. It does not retrain the model, edit its own prompts, manufacture preferences or guarantee monotonic improvement. Bounded feedback ages out; continued use supplies current evidence rather than building an indefinite personality ledger. Optional votes are a selective sample: an unvoted reading is neither a success nor a miss. Longer-lived style memory would require a separate inspectable/clearable retention decision, not an unmentioned side effect. Product-wide changes to prompts and policies follow the separate engineering cycle below.

## Common logic, separate evidence

All adapters follow the same lifecycle and meanings. They keep their existing owners and privacy domains; a common policy interface does not require a common raw-history store.

| Stage | Required behavior |
|---|---|
| Select | Read authorized, current evidence after required initial sync. Apply that surface's eligibility and user intent. Missing data stays unknown. |
| Prepare | Recompute bounded same-surface guidance from retained feedback. Keep factual input distinct from wording guidance; old outputs are not present facts. No eligible feedback means the baseline behavior. |
| Generate | Make the existing requested/eligible call within its delivery budget. Feedback adds no background call. Current automatic model-critic/rewrite budget is zero. Existing transport/length recovery keeps its own bounded contract. |
| Validate | Apply the surface's format, provenance and grounding guards. A rejected output or failed request is a technical outcome, never a user dislike or category retirement. Mechanical validation cannot certify usefulness. |
| Show | Attribute the exact result to its owner and source generation only when actually rendered. A returned request, off-screen pending result or cached object is not exposure. |
| Respond | Save an optional explicit reaction or the existing meaningful action. Persist first; then acknowledge, allow revision/clear and offer Undo where appropriate. Never reinterpret dismissal of a UI as a negative vote without an explicit contract. |
| Adapt | Revisions and clears replace earlier evidence. Produce a fresh bounded projection for the next eligible generation or selection. No regeneration solely because a vote changed; accepted daily readings and intentional silence remain stable. |
| Invalidate | Edits, deletion, source expiry, consent withdrawal, owner changes and stale responses remove the affected influence. Sync and old-backup replay cannot resurrect withdrawn feedback. |

**Feedback has different strengths.** An explicit landed/missed reaction judges a whole response, not its factual truth or a particular stylistic property. Apply/keep is intent, not success. A completed suggested step is stronger outcome evidence, but does not establish that the suggestion caused completion. Link clicks, focus duration, no click and background time do not establish satisfaction. Task completion does not prove Focus Ask was helpful. Existing post-add exposure-qualified ignore remains its narrowly documented delivery signal, not a universal definition of dislike.

**Style belongs in every writing adapter.** Preserve TODAY's common voice, then use supported same-surface feedback to inform clarity, tone, rhythm and specificity. Do not equate shortness with quality, require a particular sentence shape, infer a dislike reason from a vote, or turn one reading into a durable preference. Contradictory/sparse history keeps baseline wording guidance. The recent two-positive/two-negative sampling in 15A is a bounded initial context policy, not a learned style profile or proof of a preferred tone. Cross-surface style transfer is not enabled by this contract: feelings, dream interpretations, email content and ordinary task feedback remain separate.

## Shared implementation contract

Use the existing pure `assets/feedback-policy.js` where its contracts genuinely match. Generalize shared helpers only when a second concrete adapter needs them, rather than creating a second AI orchestrator. Components continue to own UI, calls and persistence. Adapters normalize these operations: identify a displayed result, validate feedback against current sources, project eligible guidance, and invalidate stale influence. This is a proposed shared interface, not an existing exported API.

For new multi-result feedback, identify **the exact displayed wording/card, surface subtype, owner, source generation and writing-policy version**. An identity digest is not anonymization. Event ordering needs an unambiguous revised/cleared reaction timestamp; clear needs a deletion watermark. A vote must never slide onto newer wording or another task. Keep stable claim identity separate from writing-policy version: changing a prompt or paraphrase cannot bypass a missed feeling claim or retired pool kind. Store only what is necessary for identity, bounded feedback and inspection, not a new full evidence/interaction log.

The old one-spoken-line-per-surface-per-day record cannot safely identify several Focus Ask results. Do not reuse `focus question + date` as an exact-reading feedback key or change the merge meaning of existing fields. New Focus/enrichment storage must be specified in Data/Sync before runtime writes: bounded retention/cap, payload fields, old-client behavior, LWW including clear, source deletion, memory clear and stale-backup protection. Thirty days is the candidate maximum for new voted-response retention, not approval for sixty records per new subtype. Before writes, set both per-domain record/byte caps and a total backup-size budget; specify whether prose is stored only after an explicit vote and what that consent explains. Existing data is not silently migrated or repurposed. No new record schema/cap is approved by this document alone; no implementation may silently enlarge a store. Reuse current stores where they meet the contract. Sensitive reflections retain their separate thirty-day/sixty-record/250,000-character bounds.

Historical wording and external source text are untrusted data, not instructions or current facts. Keep their scope explicit, bound them, and cover instruction-like text in isolation tests. Feedback never authorizes more mailbox/Calendar/dream access or autonomous actions.

Guidance is derived afresh, not saved as a durable personality profile. Clearing its supporting feedback removes its influence. A current positive reaction may favor supported wording patterns; it cannot bypass qualification, validate facts or force repeated content. A negative reaction may guide an alternative presentation without retiring a whole topic unless that surface explicitly has category retirement.

For feelings, historical sentences cannot be exported as examples. The current fixed opening/verbatim contexts, unchanged-result reuse and sparse whole-reading votes provide little style variation or attribution; a fictional projection test cannot establish Can’s preferences. Do not make a content-free projection the assumed mechanism, replace it with hardcoded variant optimization, or resolve this merely by asking for more historical prose. Personal style is still required but technically undesigned. Baseline writing can improve through a concrete versioned defect/copy change while the personal mechanism remains open. Any future wording freedom must preserve population/comparison/direction and source fences.

Feedback UI uses the existing optional native reaction patterns, typography and tokens, with exact-result ownership, Undo/revision/clear, accessible naming, keyboard access and mobile wrapping. No new panel, expanded ledger or interruption of focus. Actual component review precedes Focus/enrichment UI changes. Merely dismissing Ask continues to mean dismiss, not “not useful.”

## Engineering improvement cycle

Normal adaptation and product development have different clocks:

1. **Normal use automatically updates the next eligible response.** This requires no model judge, manual batch, new prompt version or user review ritual.
2. **A concrete failure triggers a versioned engineering change.** Specify the defect and surface rubric; preserve a fictional original plus acceptable controls; compare the candidate without discarding failures. Do not keep rerunning the same broad study seeking a win.
3. **Automated checks protect each change.** Pure adapter tests cover bounds, isolation, revision/clear and sparse/conflicting histories. Browser tests cover natural trigger → actual display → reaction/action → next trigger, plus sync/deletion/late replies and accessibility. Run these in the existing gate. Default CI uses fictional data and mocked providers, not Can's records or credentials.
4. **Model-based checks are development evidence only.** The existing evaluator covers nudges/feelings, not every surface. Extend a rubric only for an actual implementation: Focus help checks consequential clarification/supported action, enrichment checks cited-source fidelity/relevance, extraction checks faithfulness, dreams check grounded tentative interpretation. Assess clarity/tone separately from factual validity and personal usefulness. A judge PASS is not a user verdict.
5. **Release changes with an honest status.** Required functional, payload and performance gates; version/SW, both changelogs, architecture/Data/Sync as affected, and a dated real-use checkpoint. Preserve failed timings and originals. Failure behavior is surface-specific: ordinary nudges may use their existing legacy context; future Focus/enrichment may use a valid baseline only when owner, permission and source checks still pass. If a feeling helper cannot enforce consent or claim withholding, hide rather than expose a previously missed claim. Never treat missing deletion/consent state as empty feedback.
6. **Use real feedback to keep, iterate or remove.** Routine votes/actions feed the runtime automatically. At the existing fourteen-day review, inspect concrete readings/misses and actual context-path provenance privately if authorized. Do not use optional landed/missed rates as success estimates; context versus fallback readings from different tasks/dates are not a paired causal comparison. Do not promise statistical improvement from this selective personal sample. Technical reliability and useful writing have separate verdicts. No new analytics, background judge scores or raw-data export.

No per-output automatic critic is included. The completed study falsely rejected supported writing and weakened some acceptable results. Any future repair must have a demonstrated surface-specific benefit, a fixed total request/time budget, and a defined deadline/fallback. It is not necessary for feedback adaptation to work.

Can should not paste more repeated console batches to operate this system. If a future bounded live comparison is genuinely required and credentials are unavailable to developer tooling, resolve that access constraint once through an explicitly approved development path; do not read app/keychain credentials, change routing or turn manual packet execution into the product loop. Missing access is a limitation to report, not permission to ship unverified signal pickup.
