| **2.38.2** | **Fix: "Add tasks" in meeting review did nothing.** Can's report. Root cause: a regression from v2.37.4's speaker-tracked attribution work — `_meetingAccept()`'s new attribution-counting block referenced a bare `state.items` copy-pasted from `_meetingRenderReview(state)`'s body, but `_meetingAccept()` has no `state` parameter or local variable. That's a `ReferenceError` the instant the button is clicked, thrown inside a `forEach` callback with nothing to catch it — the whole function aborts before `manualTasks.push()` ever runs, so every accepted item silently vanished. Fixed by referencing `_mtg.items` (the actual live object) instead, guarded with `&& _mtg` since `_mtg` is only set during a live/just-ended meeting. **Also:** the meeting review panel (`#meetingPanel`) now keeps its head ("Meeting" eyebrow, "From your call" title) and its Add/Discard action row fixed in place while only `#meetingItems` scrolls — was previously one scrolling unit (`overflow-y: auto` on the whole panel), same structure the triage overlay still uses today. Converted to `display:flex; flex-direction:column` with `flex-shrink:0` on the head and actions and `overflow-y:auto; min-height:0` on the items list — the `min-height:0` is what lets a flex child actually shrink below its content size and scroll instead of just growing the panel. |
| **2.38.1** | **Polish: two proactive AI observations tuned after a direct review.** Can asked whether `big_clear`/`yesterday_win` and the reactive/intentional day-shape observations needed optimizing, following the v2.38.0 Noticed-expansion work. Findings: (1) `yesterday_win` is already rare by construction (needs the 5+-in-a-day moment AND falls on the one eligible calendar day) but was `priority: 'medium'` — a 50% coin flip on top of an already-sparse signal meant real, rare moments could go unmentioned. Bumped to `high`. (2) the day-shape observation (reactive vs. intentional, `assets/insights.js`) reads a *standing* behavioral state, not a one-time event — once a real habit crosses the threshold it can stay crossed for weeks, and the only throttle was a 24h same-type cooldown + 20% daily roll. Fixed with the same mechanism the Noticed peak-hour signal already uses: new `appMemory.patterns.dayShapeState` tracks the last-shown state ('reactive'/'intentional'/null), and the observation only fires again when that state actually *changes* — not on mere persistence. A borderline day near the threshold doesn't cause re-firing since the state only updates on a genuine crossing, not every evaluation. |

| **2.37.8** | **Fix: BUG-061 — Sunday/habit badges could silently fail on a fresh device (same root cause as BUG-060).** Found by audit, not yet reported: `checkSundayNudge()` reads `today_daily_history` and `checkHabitNudge()` reads `habitsList`/`habitCompletions` — both genuinely Dropbox-synced, both read from module-level variables initialized once at script-parse time. | **2.37.7** | **Fix: BUG-060 — completed Trello card reappeared as active on a fresh device connect.** Can's report: an old, overdue Trello task he'd already completed showed up on the list when he connected a new desktop PWA. Root cause: `loadTrello()` fires from `init()` before Dropbox restore lands, so `doneIds` is still an empty `Set` on a genuinely fresh device — the completed card's own Trello record has no local "done" flag yet, so it passes the "overdue, not done → show" filter. This would normally self-correct on the next 7s ticker cycle, except `syncTrello()` only re-fetches Trello when the board's own `dateLastActivity` changes — and that value gets seeded to current *before* the Dropbox merge runs, and never changes again since the completion only ever happened in TODAY, never on the real Trello card. Same bug class as `checkTriageBar()`/`checkDayNudge()`'s existing post-merge re-checks — `loadTrello()` had never been given one. New `_reconcileTrelloAfterMerge()` in `trello.js`, called right after `mergeRemoteData()` in the load handler: re-filters the already-loaded `trelloTasks` against the now-correct `doneIds` using the same done+grace-window rule `loadTrello()` already applies. No extra Trello API call. |
| **2.37.6** | **Fix: morning nudge could be generated minutes before it was actually read.** Can's report: the nudge sometimes referenced tasks he'd already checked off by the time he saw it. Root cause: `checkDayNudge()` fires from `init()` before the Dropbox sync pull lands (the new-day-cleanup code has an explicit comment about waiting for this same reason; the nudge check didn't). Since the AI nudge generates once per day and caches permanently (`day_nudge_ai_<date>`, never regenerated for the rest of that day), whichever call happens to be first to find no cache "wins" — and until now that was always the pre-sync `init()` call, using whatever state this device had before it heard from Dropbox. `checkDayNudge()` now takes an `allowGenerate` param (default `true`); the `init()` call passes `false` — it can still show an already-cached line, just can't be the one to generate for the first time. Every other call site (post-restore, remote `day_nudge_ai` arrival, and the post-sync re-check already in the `window 'load'` handler) keeps default `true`. Net effect: on a genuine cold start, the post-sync re-check — which fires right before `_appLoadDone` gates splash dismissal — becomes the one generating the nudge, so it reads the just-synced, cross-device-current task list, and generation overlaps time already being spent on the splash animation instead of adding a new wait. |
