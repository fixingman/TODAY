| **2.38.8** | **Fix: morning nudge showed yesterday's cached AI text after the tab stayed open across midnight.** Can's report: a task he'd completed before midnight was described as still pending, and the task count was wrong (16 vs. actual 12). Root cause: `checkNewDay()` (`index.html:9031`) handles the full day-rollover cleanup — tasks, habits, Trello, stats — but never touched the nudge banner. The AI nudge's cache key (`day_nudge_ai_<date>`) is correctly date-scoped by design, but nothing re-checks it against the new date once midnight passes during an already-open session — the banner's DOM just keeps showing whatever was rendered pre-midnight. Compounding this: the `_nudgeRendered` session guard added in v2.38.4 (to stop cross-call-site re-renders) is a per-page-load flag — once the pre-midnight nudge rendered, that flag was already `true`, so even calling `checkDayNudge()` on rollover would have silently no-op'd. Fix: `checkNewDay()` now resets `_nudgeRendered`/`_nudgeRacing` to `false` and calls `checkDayNudge()` as part of its day-boundary sequence, alongside the existing task/habit/Trello/stats refresh — so a tab left open overnight gets a genuinely fresh nudge generation for the new day, not a replay of the old one. |
| **2.38.7** | **Fix: dragged manual task snaps back to old position ~1s later (drag jump-back).** Can's report, noticed after v2.38.5. Root cause: `mergeRemoteData()` ordered manual tasks remote-order-wins with no recency guard. The `_pendingBackup` flag prevents the 7s ticker from reverting a fresh drag, but the **initial load pull** and **reconnect pull** don't check it. On a warm refresh (reopened within 30 min → splash skipped → app interactive instantly) the initial Dropbox pull is still in flight when the user drags; it resolves carrying the pre-drag order and applies it over the drag. Trello order got a recency guard back in BUG-042; manual order never did. v2.38.5's earlier sync kickoff shifted *when* the initial pull lands, which is why it surfaced then — but the missing guard is the real, pre-existing flaw. **Fix (mirrors BUG-042):** new `today_manual_order_at` ISO stamp set on every manual reorder (drop handler + touch `_saveOrder`), synced as `manual_order_at` (schema 5.3 → 5.4). In `mergeRemoteData`, the order basis is chosen by recency — remote wins by default, but a strictly-newer local reorder stamp keeps the local sequence for shared tasks (remote-only additions still append at end, local-only after that, all zone/delete filters unchanged); on remote-wins the device adopts the remote stamp so the next merge compares correctly. Absent stamp (old backup) → `''` → remote wins = exact prior behavior, no migration. Fixes every pull path (initial, ticker, reconnect, wake), not just the one that surfaced. Detail → `architecture/Sync.md`. |
| **2.38.6** | **Fix: morning nudge kept defaulting to the top task despite v2.36.6's anti-echo instruction.** Can's report: it always mentions task 1, wanted it to look at the whole list and surface the most important/hard task instead. Root cause: the prompt (`_fetchDayNudgeAI`) contained a contradiction — it told the model *"position 1 is where the user put their priority"* in the same breath as *"do not echo the top item just because it is first."* The model resolved that the easy way: keep mentioning task 1, just justified as "priority" instead of "position," technically obeying the anti-echo clause's literal wording while still landing on the same task every time. TODAY has no priority/due-date/label field by design (Philosophy.md walls), so "importance" can only be inferred from behavior, never looked up — the fix reframes what's inferred from, not what's stored. Removed the position-as-priority framing entirely (facts block now says "in the order the user arranged things," no "position reflects intent" language). Instruction now explicitly ranks signals: focus sessions spent without being done ("stuck, not just old") as the strongest hard-task signal; revived tasks and overdue Trello cards next; position is named explicitly as sequence, not importance, and forbidden as a standalone reason. Same verbatim-quote requirement and quiet-when-nothing-stands-out fallback kept from v2.36.6. |
| **2.38.5** | **Perf: sync now starts right after `init()` instead of waiting for `window.load`.** Can's question: shouldn't sync begin as soon as the splash animation starts, so it's mostly ready by the time you land in the app? Traced the risk before implementing (Non-Delegation Zone — sync merge logic): `window.load` waits for *every* subresource — both fonts, both icon PNGs, the OG-image meta tag's image, all 11 splash launch-screen PNGs — while the splash animation itself only waits on fonts (`document.fonts.load()` raced against a 2000ms ceiling). That gap meant sync sat idle even after everything the splash actually needed was ready. Splash dismissal already only depends on sync *finishing* (`_appLoadDone`), not on when it started, so starting earlier can only shorten the wait, never lengthen it. Traced two things that could have broken: `startTicker()`'s rev-seed-before-first-tick ordering (safe — it's called from inside the same async function being moved, so the internal sequence travels with it unchanged) and `_appReady` (safe — gated on splash-dismiss completing, not sync start time). Removed the `window.addEventListener('load', ...)` wrapper around the sync-kickoff block; it now runs as a plain block right after `init()`, still wrapped in the same `setTimeout(0)` yield the code already used to avoid blocking first paint. `init()`'s own synchronous execution still guarantees the sync code's `await`ed continuations can't run before `init()` finishes — nothing about that ordering changed. |
| **2.38.4** | **Fix: morning nudge could swap content a second after it appeared.** Can's report on desktop: the nudge shows a message, then the content changes mid-way, a second later. Root cause: `checkDayNudge()` has multiple call sites (init, wake, Dropbox restore, the post-sync load handler), and `_raceAINudge()`'s "settled" flag only prevents a swap *within one call's own race* — it can't stop a later, separate call site from finding a freshly-written cache (written by an earlier call's AI fetch resolving just after its own 1s timeout had already shown the rule-based fallback) and re-rendering with the new text. Concretely: call site A's race times out at 1s and shows the fallback; its AI fetch keeps running in the background and writes the real text to cache moments later; call site B (e.g. the ticker's first tick, ~2s after load, which always treats a null `lastDropboxRev` baseline as "changed") runs `checkDayNudge()` again, finds that fresh cache, and re-displays it — a visible swap the "never replace once shown" design was supposed to prevent, just from a call site it didn't know about. Fixed with two session-level guards (not per-race): `_nudgeRendered` blocks any further render once one has happened this page load, from any call site; `_nudgeRacing` stops a second call site from starting its own parallel race while one is already in flight, avoiding a wasted duplicate AI fetch too. |
| **2.38.3** | **Fix: faint shadow over the top task on hover.** Can's report. Root cause: `.section-header::after`'s fade gradient (z-index 9, deliberate design — comment says "tasks dissolve under the pinned label instead of clipping at a hard edge") always overlaps the top ~10px of whatever sits directly beneath it, regardless of scroll position. At rest, the task's background blends into the gradient invisibly; `.task:hover`'s `--surface` background contrasts against the same permanent overlap enough to read as a visible shadow band — a rendering artifact of an always-on effect, not something tied to scrolling at all. Fixed by giving `.task:hover` `z-index: 10` so the hovered task paints above the gradient layer instead of underneath it. The gradient itself — and its behavior while actually scrolling — is untouched; this only changes stacking order for the hover state. |
| **2.38.2** | **Fix: "Add tasks" in meeting review did nothing.** Can's report. | **2.38.1** | **Polish: two proactive AI observations tuned after a direct review.** Can asked whether `big_clear`/`yesterday_win` and the reactive/intentional day-shape observations needed optimizing, following the v2.38.0 Noticed-expansion work. | **2.37.7** | **Fix: BUG-060 — completed Trello card reappeared as active on a fresh device connect.** Can's report: an old, overdue Trello task he'd already completed showed up on the list when he connected a new desktop PWA. Root cause: `loadTrello()` fires from `init()` before Dropbox restore lands, so `doneIds` is still an empty `Set` on a genuinely fresh device — the completed card's own Trello record has no local "done" flag yet, so it passes the "overdue, not done → show" filter. This would normally self-correct on the next 7s ticker cycle, except `syncTrello()` only re-fetches Trello when the board's own `dateLastActivity` changes — and that value gets seeded to current *before* the Dropbox merge runs, and never changes again since the completion only ever happened in TODAY, never on the real Trello card. Same bug class as `checkTriageBar()`/`checkDayNudge()`'s existing post-merge re-checks — `loadTrello()` had never been given one. New `_reconcileTrelloAfterMerge()` in `trello.js`, called right after `mergeRemoteData()` in the load handler: re-filters the already-loaded `trelloTasks` against the now-correct `doneIds` using the same done+grace-window rule `loadTrello()` already applies. No extra Trello API call. |
| **2.37.6** | **Fix: morning nudge could be generated minutes before it was actually read.** Can's report: the nudge sometimes referenced tasks he'd already checked off by the time he saw it. Root cause: `checkDayNudge()` fires from `init()` before the Dropbox sync pull lands (the new-day-cleanup code has an explicit comment about waiting for this same reason; the nudge check didn't). Since the AI nudge generates once per day and caches permanently (`day_nudge_ai_<date>`, never regenerated for the rest of that day), whichever call happens to be first to find no cache "wins" — and until now that was always the pre-sync `init()` call, using whatever state this device had before it heard from Dropbox. `checkDayNudge()` now takes an `allowGenerate` param (default `true`); the `init()` call passes `false` — it can still show an already-cached line, just can't be the one to generate for the first time. Every other call site (post-restore, remote `day_nudge_ai` arrival, and the post-sync re-check already in the `window 'load'` handler) keeps default `true`. Net effect: on a genuine cold start, the post-sync re-check — which fires right before `_appLoadDone` gates splash dismissal — becomes the one generating the nudge, so it reads the just-synced, cross-device-current task list, and generation overlaps time already being spent on the splash animation instead of adding a new wait. |
